# 04 — หลักการคำนวณหลัก (Core Methodology)

> **เอกสารฐาน 04 ของโครงการ** · `formula_version = 1`
> **วันที่จัดทำ:** 23 พศ. 2568 · **สถานะ:** Draft — **รอ Gate 2 ยืนยันน้ำหนัก/เกณฑ์** (DEC-003)
> **หมายเหตุความเข้ากัน:** โปรโตไทป์ปัจจุบัน (`mobile/app/lib/services/alert_engine.dart`) ใช้เกณฑ์ `situation_level` เป็นหลัก
> สูตรในเอกสารนี้คือ **เป้าหมาย**ที่ pipeline จะคำนวณ และแอพจะแสดงผลเชิงขนาน (cross-check)

---

## 1. สูตร Alert Score

```text
Alert Score = 0.5 × W + 0.25 × R + 0.15 × F + 0.10 × C
```

| ตัวแปร | ความหมาย | น้ำหนัก | ช่วง | แหล่ง |
|---|---|---:|---|---|
| **W** | ระดับน้ำ (น้ำหนักหลัก) | 0.50 | 0–1 | ThaiWater `waterlevel_msl` + `left_bank` |
| **R** | ฝนจริง | 0.25 | 0–1 | TMD `rain_1h` (ยังไม่ผูก) |
| **F** | พยากรณ์ฝน | 0.15 | 0–1 | TMD `forecast_24h` (ยังไม่ผูก) |
| **C** | รายงานชุมชน | 0.10 | 0–1 | รายงานในแอพ (trust ≥ 3) |

คะแนนรวม = `round(100 × (0.5W + 0.25R + 0.15F + 0.10C), 1)` แล้ว `clamp(0, 100)`

> เหตุผลของน้ำหนัก: ระดับน้ำเป็นตัวทำนายที่น่าเชื่อถือที่สุด; **ฝนอย่างเดียวไม่ push** (ดูข้อ 6)

---

## 2. กฎ Normalization (W / R / F / C)

### 2.1 W — ระดับน้ำ (0.50)

**สูตรหลัก**

```text
W = clamp((H − H_normal) / (H_bank − H_normal), 0, 1)
```

| ตัวแปร | ความหมาย | แหล่ง | กฎ |
|---|---|---|---|
| `H` | ระดับน้ำล่าสุด | `waterlevel_msl` (ถ้าไม่มีใช้ `waterlevel_m`) | ต้องเป็นตัวเลข |
| `H_bank` | ระดับตลิ่ง | `left_bank` → `right_bank` → `min_bank` | **ต้อง > 0** ไม่อย่างนั้น W=0 |
| `H_normal` | ระดับน้ำปกติ | **median 30 วัน** ของสถานีเดียวกัน | bootstrap เริ่มต้นด้วย `H_bank − 2.0` ม. |

**กฎเพิ่มเติมสำหรับ W**

| กรณี | พฤติกรรม |
|---|---|
| `H_bank <= 0` หรือขาด | `W = 0` และ `water_signal = false` (ไม่คำนวณ W) |
| ข้อมูลเกิน 30 นาที | `W = 0`, `stale = true` (fail-closed) |
| ไม่มีตลิ่งแต่มี `situation_level` | ใช้ `W = situation_level / 4` (1→0.25, 2→0.50, 3→0.75, 4→1.00) |
| ไม่มีทั้งสองอย่าง | `W = 0`, `water_signal = false` |
| `situation_level` มีค่า | ใช้เป็น **floor ของระดับ** (ดูข้อ 5) และตั้ง flag เมื่อขัดกัน |

### 2.2 R — ฝนจริง (0.25)

```text
R = clamp(rain_1h / 60, 0, 1)        // ค่าอิ่มตัว 60 mm/h
```

| กรณี | พฤติกรรม |
|---|---|
| ขาดข้อมูล | `R = 0`, `rain_stale = true` |
| ข้อมูลเกิน 60 นาที | `R = 0` (ตาม AC-003) |
| ยังไม่มี API TMD | `R = 0` จนกว่าจะผูก (Phase 1) |

### 2.3 F — พยากรณ์ฝน (0.15)

```text
F = clamp(forecast_24h / 120, 0, 1)   // ค่าอิ่มตัว 120 mm/24h
```

| กรณี | พฤติกรรม |
|---|---|
| ขาดข้อมูล | `F = 0` |
| ยังไม่มี API TMD | `F = 0` จนกว่าจะผูก |

### 2.4 C — รายงานชุมชน (0.10)

```text
C = clamp(report_count_60min / 5, 0, 1)   // ค่าอิ่มตัว 5 รายงาน/ชม.
```

| กฎ | เหตุผล |
|---|---|
| นับเฉพาะ `trust_score >= 3` | กันสแปม (ตาม AC-403) |
| จำกัด 1 รายงาน/ผู้ใช้/ชม. | กันผู้เดียวกันเดดให้ C=1 (ตาม AC-402) |
| ทุก 60 นาที | กันรายงานเก่า |

### 2.5 ค่าเริ่มต้นเมื่อขาดข้อมูล (สรุป)

| ตัวแปร | ค่าเมื่อขาด | flag |
|---|---|---|
| W | 0 (ยกเว้นใช้ situation mapping) | `water_signal=false` |
| R | 0 | `rain_stale=true` |
| F | 0 | — |
| C | 0 | — |

> **ผลกระทบณ ปัจจุบัน:** เพราะ TMD ยังไม่ผูก และข้อมูลย้อนหลังยังไม่มี สูตรใน production จึงพึ่ง
> `W` (จากระดับน้ำ/ตลิ่ง) และ `situation_level` เป็นหลัก — ต้องตั้ง `formula_version=1` และ log ค่าที่ขาดทุกรอบ

## 3. ตารางเกณฑ์ระดับ 1–5

| ระดับ | ชื่อ | ช่วงคะแนน | คำแนะนำต่อผู้ใช้ | สี | situation_level ที่ควร |
|---:|---|---|---|---|:--:|
| 1 | ปกติ | 0–19 | ดูได้ตามปกติ | เขียว `#2E7D32` | 1 |
| 2 | เฝ้าระวัง | 20–39 | ติดตามข่าว เตรียมถุงยังชีพ | เหลือง `#F9A825` | 2 |
| 3 | เตือนภัย | 40–59 | เตรียมอพยพ ย้ายของสำคัญ | ส้ม `#EF6C00` | 3 |
| 4 | เตือนภัยสูง | 60–79 | พร้อมอพยพทันที ติดต่อเจ้าหน้าที่ | แดงอ่อน `#EF5350` | 3–4 |
| 5 | อันตราย | 80–100 | **อพยพทันที** ไปจุดพักพิง | แดงเข้ม `#C62828` | 4 |

### 3.1 เกณฑ์ระดับ (pseudocode)

```text
level_from_score(s):
  s < 20  -> 1
  s < 40  -> 2
  s < 60  -> 3
  s < 80  -> 4
  else    -> 5
```

### 3.2 ความเข้ากับโค้ดปัจจุบัน

| ระบบ | ระดับ | หมายเหตุ |
|---|---|---|
| `RiskLevel` (prototype) | 4 ระดับ: unknown/normal/watch/warning/danger | ใช้ `situation_level` + ตลิ่ง |
| Alert Score (เป้า) | 5 ระดับ | ใช้ใน snapshot/UI หลัก |
| การ map | `normal→1`, `watch→2`, `warning→3`, `danger→4–5` ตามคะแนน | ต้องแสดง "ที่มา" ทุกครั้ง |

## 4. Override สำหรับเขตน้ำท่วมฉับพลัน (Flash Flood)

**เขตที่ใช้:** บันนังสตา, กรงปินัง, เบตง, กาบัง, ธารโต (5 อำเภอ)

| เงื่อนไข | ผล |
|---|---|
| `R >= 0.7` (ฝนจริง ≥ 42 mm/h) | ยกระดับขึ้นอย่างน้อย 1 ระดับ |
| `C >= 0.6` (≥ 3 รายงาน/ชม.) | ยกระดับขึ้นอย่างน้อย 1 ระดับ |
| ทั้งสองเงื่อนไขเข้า | ยกได้สูงสุด 2 ระดับ |
| ทุกกรณี | **ไม่เกินระดับ 5** |

> เหตุผล: เขต flash flood น้ำท่วมใน 2–4 ชม. ระดับน้ำสถานีอาจยังปกติ ต้องเร่งน้ำหนักฝน/รายงานชุมชน
> **คำขอ Gate 2:** ยืนยันว่ากฎ +1/+2 ไม่ทำให้ false alarm สูงเกิน (KPI-4 ≥ 90%)

---

## 5. Hysteresis, Cooldown และ Floor

### 5.1 กฎ Floor จากเกณฑ์หน่วยงาน

```text
situation_floor_level = clamp(situation_level, 1, 4)   // ถ้ามีค่า
base_level = max(level_from_score(score), situation_floor_level)
```

> สูตรต้อง **ไม่ลดระดับ** จากเกณฑ์ที่หน่วยงานประกาศไว้
> ถ้า `situation_level >= 3` แต่ W ต่ำ ให้ตั้ง `flag = situation_score_mismatch` (ไม่บังคับยก W)

### 5.2 Hysteresis (ล็อกระดับสูง)

| กฎ | ค่า |
|---|---|
| ระดับสูงล็อก | 2 ชั่วโมง |
| เมื่อคะแนนลดภายใน 2 ชม. | คงระดับเดิมไว้ (ยกเว้นมี override ใหม่สูงกว่า) |
| เมื่อคะแนนเพิ่มขึ้น | อัปเดตทันที (ไม่รอ hysteresis) |

### 5.3 Cooldown การแจ้งเตือน

| กฎ | ค่า |
|---|---|
| ไม่ส่งซ้ำภายใน | 30 นาที |
| ยกเว้น | ระดับสูงขึ้น → ส่งทันที |
| ประวัติคะแนน | เก็บย้อนหลัง ≥ 30 วัน |

## 6. หลักการ "ฝนอย่างเดียวไม่ Push"

**เป้าหมาย:** ป้องกัน notification fatigue และ false alarm จากฝนที่ตกในยะลาบ่อยครั้งแต่ไม่ถึงบ้าน

| # | กฎ | ตัวอย่าง |
|---|---|---|
| 1 | push เริ่มที่ **ระดับ 2** เป็นต้นไป (ระดับ 1 ไม่ push) | score 12.5 → ระดับ 1 → ไม่ push |
| 2 | ต้องมี **สัญญาณหลัก** อย่างน้อย 1 อย่าง: `W > 0` หรือ `situation_level >= 2` หรือ `C >= 0.6` | W=0, R=0.9 → ไม่ push |
| 3 | ถ้ามีแต่ `R > 0` (ฝนอย่างเดียว) → **ไม่ push** | R=0.9, W=0, situation=null → ไม่ push |
| 4 | override เขต flash flood (R≥0.7) ยกระดับ แต่ **ยังต้องมีสัญญาณหลัก** ถึงจะ push | R=0.8, C=0.6 → push; R=0.8, C=0 → ไม่ push |
| 5 | push เฉพาะอำเภอ/หมู่บ้านที่ผู้ใช้ subscribe | ไม่ส่งข้ามเขต |
| 6 | แสดงคะแนนบนแอพได้ทุกกรณี (ไม่ห้ามแสดง) | ผู้ใช้เปิดเอง |

> **หลักการ:** ฝนเป็น "ตัวเร่ง/ตัวขับ" ไม่ใช่ "ตัวตัดสิน" — ต้องมีหลักฐานว่าน้ำมาถึง/กำลังมาถึง
> ยกเว้นเขต flash flood ที่ฝนภูเขาเป็นสัญญาณเดียวที่ "รวดเร็วพอให้ใช้เป็นเกณฑ์" (รอ Gate 2)

## 8. Station Registry Schema (registry_version=1)

> Registry คือแหล่งความจริงของสถานี/ตลิ่ง/พิกัด — **ไม่ hardcode ในโค้ด** (ตาม AGENTS.md §5)
> เปลี่ยน registry ต้องผ่าน Gate 2; registry มี hash เช่นกัน

```json
{
  "registry_version": 1,
  "province_code": "95",
  "stations": [
    {
      "code": "PAT002",
      "source_id": 1345491088,
      "name_th": "เมืองยะลา",
      "name_en": "Patthani 2",
      "river": "เขื่อนปัตตานี",
      "amphoe_th": "เมืองยะลา",
      "tumbon_th": "ตาเซะ",
      "lat": 6.67525,
      "lon": 101.286354,
      "left_bank": 13.85,
      "right_bank": 13.85,
      "min_bank": 13.85,
      "ground_level": 1.74,
      "agency_shortname_th": "สสน.",
      "flash_flood": false,
      "default_situation_level": null,
      "active": true
    }
  ]
}
```

| Field | ประเภท | บังคับ | ความหมาย | แหล่ง |
|---|---|:--:|---|---|
| `code` | string | ✅ | รหัสสถานี (`tele_station_oldcode`) | API |
| `source_id` | int | ✅ | id ใน API (`id`) | API |
| `name_th/name_en` | string | ✅ | ชื่อ | API |
| `river` | string | | แม่น้ำ/คลอง | API `river_name` |
| `amphoe_th/tumbon_th` | string | ✅ | อำเภอ/ตำบล | API `geocode` |
| `lat/lon` | number | ✅ | พิกัด | API |
| `left_bank/right_bank/min_bank` | number | | ตลิ่ง (ม.รทก.) | API `station` |
| `ground_level` | number | | ระดับพื้นดิน | API `station` |
| `agency_shortname_th` | string | | หน่วยงาน | API `agency` |
| `flash_flood` | bool | ✅ | เขตน้ำท่วมฉับพลัน | ทีม/หน่วยงาน |
| `default_situation_level` | int/null | | เกณฑ์เริ่มต้น | หน่วยงาน |
| `active` | bool | ✅ | เปิดใช้งาน | ทีม |

### 8.1 กฎใช้ registry

| กฎ | พฤติกรรม |
|---|---|
| จับคู่ | จับคู่ระหว่าง registry กับ API ด้วย `code` |
| ข้อมูลขาด | ใช้ค่าจาก registry (เช่น ตลิ่ง) และตั้ง flag |
| ไม่ตรงกัน | ห้ามเขียน snapshot ที่มี `code` ไม่มีใน registry (ยกเว้นเพิ่มสถานีใหม่ผ่าน Gate 2) |
| เปลี่ยน registry | ต้องผ่าน Gate 2 + unit test + บันทึก changelog |

## 9. การคำนวณ H_normal (bootstrap)

| ขั้น | เงื่อนไข | วิธี |
|---|---|---|
| 1 | มีประวัติ ≥ 30 วัน | `H_normal = median(waterlevel_msl)` ของสถานีนั้น |
| 2 | ยังไม่ครบ 30 วัน | `H_normal = H_bank − 2.0` ม. (หรือค่าจาก situation) + `h_normal_confidence=low` |
| 3 | ไม่มีตลิ่ง | `W = situation_level/4` (ไม่คำนวณ W จากสูตรหลัก) |
| 4 | ประวัติ | เก็บ history ตั้งแต่ Phase 1 (เป้า RPO ≤ 10 นาที) |
